# Executive Storyline Guide

Use this guide for management, executive, steering-committee, board, proposal,
strategy, or major-project decks. Treat the deck as a decision instrument, not
as a decorated outline.

## 1. Lock The Narrative Contract

Before planning pages, write four items:

- `core_thesis`: the single judgment the audience should remember. Make it a
  specific conclusion, not a topic such as "AI 建设汇报".
- `decision_request`: the decision, approval, alignment, or next action needed
  from the audience.
- `audience_priority`: the 1-3 issues the audience will judge first, such as
  business value, risk, investment, feasibility, timing, or accountability.
- `story_arc`: 3-6 logical moves that lead from shared context to the decision.

If two plausible theses would produce materially different decks, ask the user
one focused question before fixing the page count or generating images.

## 2. Build A Causal Story, Not An Outline Dump

Choose the shortest arc that supports the decision. Common arcs:

- Proposal: why now -> current constraint -> proposed answer -> proof -> rollout
  and risk -> decision request.
- Progress review: target -> current status -> evidence -> gap and cause -> next
  move -> support required.
- Strategy: external/internal change -> strategic choice -> capability system ->
  value and trade-offs -> roadmap -> decision request.
- Solution: business problem -> design principle -> solution mechanism -> scene
  or workflow -> measurable value -> implementation and governance.

Do not preserve the source order when it weakens the argument. Merge repeated
material, move technical detail after the business judgment, and put appendices
outside the main decision path.

Use the `because / but / therefore` test:

- `because`: what evidence makes this page credible?
- `but`: what tension or unresolved question remains?
- `therefore`: why must the next page follow?

A sequence joined only by "and next" is a list, not a story.

## 3. Design Each Slide As One Argument

For every content slide define:

- `audience_question`: the question in the audience's mind.
- `message`: the answer or conclusion; use it as the basis for a conclusion-led
  title.
- `claim_type`: `fact`, `inference`, `proposal`, or `decision`.
- `facts`: source-backed evidence. Keep assumptions visibly separate from facts.
- `information_topology`: how the ideas relate, such as shared center, cause and
  effect, sequence, hierarchy, comparison, network, or evidence board.
- `visual_focus`: the dominant visual system or focus region the eye should
  understand first. It may contain several connected elements when the
  relationship itself is the message.
- `visual_reasoning`: why the chosen topology expresses the conclusion better
  than a table, bullet list, or unrelated set of cards.
- `transition.from_previous`: the logic inherited from the prior page.
- `transition.to_next`: the unresolved question or implication that opens the
  next page.
- `speaker_notes`: optional explanation; do not force all narration into the
  image.

Except for cover, chapter, and closing pages, avoid topic-only titles such as
"平台架构" or "项目成效". Prefer conclusions such as "统一知识底座是规模化复制
的前提". The title should state what is true; the visual should show why.

## 4. Control Page-to-Page Flow

- Make slide N+1 answer the question raised by slide N.
- Keep one stable visual anchor across adjacent pages when they discuss the same
  system: the same process spine, architecture layers, value dimensions, or
  roadmap axis.
- Change composition when the reasoning changes, not merely to add variety.
- End a chapter by resolving its opening question and exposing the next chapter's
  question.
- Make the final content page converge on `decision_request`; do not end with an
  unrelated capability summary.

Use short spoken bridges. A good bridge names the conclusion just established
and the next question, for example: "价值方向已经明确，下一步要回答的是这套能力
如何落到现有流程中。"

## 5. Run The Solution-Expert Review

Review the complete storyboard before any paid image generation.

### Thesis test

- Can the deck be summarized in one sentence?
- Does every slide strengthen, qualify, prove, or operationalize that sentence?
- If a slide is removed, does the argument weaken? If not, merge or delete it.

### Executive test

- Is the decision request explicit?
- Are value, feasibility, risk, investment, timing, and ownership addressed in
  proportion to the request?
- Are fact, inference, proposal, and decision clearly distinguishable?
- Does technical architecture serve the business judgment rather than become the
  story itself?

### Flow test

- Can every adjacent pair be connected with "therefore", "however", or
  "because"?
- Does each chapter open a question and close it?
- Are there abrupt jumps in time, abstraction level, actor, or scope?
- Do speaker bridges sound natural when read aloud in sequence?

### Visual test

- Is there one dominant visual system per page, even when it contains several
  connected nodes or layers?
- Does the topology match the actual relationship among the ideas?
- Are meaningful relationships visible rather than flattened into isolated
  cards or table rows?
- Is the canvas solid white or a user-approved solid brand color, with no busy
  background texture or scenic wallpaper?
- Does the contact sheet show a deliberate rhythm: establish -> explain -> prove
  -> decide?
- Are adjacent pages visibly related without repeating the same template?

Record any failed test in the plan and revise the storyboard before generation.
